# OpenClaw Mem0 + Graphiti 升级落地方案设计审计

## 审计范围

本次审计覆盖两部分：

1. 本地方案与实现：`W0-W4` 的计划文档、桥接代码、记忆栈脚本、`Gate-4` 评测与收口证据。
2. 外部资料：`Graphiti`、`Mem0`、`Neo4j`、`Qdrant` 的官方文档、官方仓库与社区问题。

本次审计的结论不是“这套方案有没有跑通”，而是：

- 这套方案是否值得继续作为 `OpenClaw` 的长期记忆升级方向；
- 现有 `W4` 收口结果里，哪些是结构性优点，哪些只是阶段性补丁；
- 进入 `W5` 之前，哪些点需要明确带着风险进入，哪些点应该优先润色。

---

## 总结先说

### 最终结论

**可以进入 `W5`，但必须带着风险清单进入。**

### 总评

这套方案的**大方向是对的**，而且在 `W4` 最终已经拿到了强质量、可接受时延和稳定性同时达标的结果。它不是“误打误撞跑通”，而是已经具备以下三个结构性优点：

1. **分层合理**：`builtin local`、`Mem0`、`Graphiti` 三层分工基本成立。
2. **回滚能力强**：由于 `OpenClaw` 的 memory slot 独占，桥接层把本地兜底内置进来了，这一点非常关键。
3. **评测纪律较好**：`memory_search` 硬门禁、单变量 `Gate-4`、`bounded + stability` 这三层门禁，说明这套方案已经不只是“感觉好”，而是开始进入“可验证”。

但它还没有成熟到“可以放心一路放大”的程度。主要原因不是质量不够，而是**设计边界还不够干净**：

- 路由、融合、回退、诊断、上下文拼装都堆在桥接层一个超大文件里；
- 关键策略很多仍然是手工规则与静态权重；
- 有些性能与部署修复是“为了这次过关很有效”，但还没有被整理成长期可维护的产品级策略。

换句话说：

> 这套方案已经证明“方向可行”，但还没有证明“设计已优雅收敛”。

### 1. `W4` 最终结果已经达标

- `fur_delta_pp = 72.58`
- `p95_increase_pct = 13.7122`
- `stability.pass = true`

说明这套方案在当前评测口径下，已经同时满足：质量提升、时延约束、稳定性约束。

相关证据：

- `analysis/2026-02-24-mem0-graphiti-value-maximization/wave4-artifacts/day33/w4-r24-gate4-single-primary-maxfacts1/report/w4-gate4-delta.json`
- `analysis/2026-02-24-mem0-graphiti-value-maximization/wave4-artifacts/day33/w4-r24-gate4-single-primary-maxfacts1/report/gate4.go-no-go.summary.json`

### 2. 当前收口时的真实工作口径是 `builtin local + bridge + mem0 + graphiti`

最终跑赢配置里：

- `memory.backend = builtin`
- `plugins.slots.memory = memory-mem0-graphiti-bridge`
- 路由为：
  - `default_route = local`
  - `semantic_route = mem0`
  - `timeline_route = graphiti`
  - `fallback_route = local`

这说明当前成功方案不是“完全远端化”，而是**本地为锚点，远端做增强**。

相关证据：

- `analysis/2026-02-24-mem0-graphiti-value-maximization/wave4-artifacts/day33/w4-r24-gate4-single-primary-maxfacts1/inputs/openclaw.config.json`

### 3. 本地层不是弱兜底，而是一个已经较强的混合检索层

本地记忆索引不是只有向量或只有关键词，而是：

- 支持向量检索；
- 支持全文关键词检索；
- 支持混合合并；
- 还带有多样性与时间衰减策略。

因此，设计上如果把本地层只理解成“远端挂了以后顶一下”，是低估了它。

相关证据：

- `src/memory/manager.ts`
- `src/memory/manager-search.ts`
- `src/memory/hybrid.ts`

### 4. `Mem0` 的作用域修复方向与官方文档一致

现在桥接层已经把 `user_id / agent_id / run_id` 作为远端搜索参数透传，这与 `Mem0` 官方把这些字段定义为搜索作用域主键的方向是一致的。

相关证据：

- `extensions/memory-mem0-graphiti-bridge/src/client/mem0-client.ts`
- `https://docs.mem0.ai/api-reference/memory/search-memories`
- `https://docs.mem0.ai/platform/features/entity-scoped-memory`

### 5. `Graphiti` 官方明确支持命名空间，并明确说限组可提升查询性能

官方文档把 `group_id / group_ids` 定位成命名空间，并明确把“缩小搜索范围以提升查询性能”列为关键收益之一。

相关证据：

- `scripts/memory-stack/backfill.py`
- `https://help.getzep.com/graphiti/core-concepts/graph-namespacing`

### 6. 当前实现还没有把 `group_ids` 用在桥接查询里

这意味着当前 `Graphiti` 仍在更大的搜索空间内工作，性能还有进一步优化空间。

相关证据：

- `extensions/memory-mem0-graphiti-bridge/src/client/mem0-client.ts`
- `extensions/memory-mem0-graphiti-bridge/src/tools/memory-search-tool.ts`

### 7. 当前 `Aura` 连接处理带有本地化兜底性质

`memory-stack` 会对 `Aura` 风格的 `neo4j+s://` 地址做自动规整，改成 `bolt+s://`。这在本地证据里是为了压住路由解析抖动，但它并不是 `Neo4j` 官方对 `Aura` 的默认推荐路径。

相关证据：

- `scripts/memory-stack/common.sh`
- `https://neo4j.com/docs/python-manual/current/connect-advanced/`

## 高置信推断

### 1. 这套方案的真正价值，不在“多接了两个远端”，而在“把记忆层做成了分层系统”

从当前实现和最终成功配置看，真正有效的不是“把所有检索都扔给 `Mem0` 或 `Graphiti`”，而是：

- `builtin local` 提供确定性、低延迟、可回滚的基础层；
- `Mem0` 负责带作用域的事实与偏好类记忆；
- `Graphiti` 负责时序关系与图侧命中；
- bridge 层负责按查询类型选择路径，并在必要时融合。

这说明它的本质是“分层记忆架构”，而不是“外挂两个数据库”。

### 2. 当前 `W4` 的成功，说明路由分工方向是对的，但不代表当前 bridge 设计已经优雅

`day31 -> day33` 的结果非常清楚：

- 质量几乎没变；
- 真正被修掉的是长尾延迟。

这说明原来的主要问题不是“远端没价值”，而是“融合执行方式不对”。

也就是说：

- 路由方向是对的；
- 但桥接策略实现曾经过重、过宽、过慢。

### 3. 当前 bridge 更像“成功的试验台”，还不是“干净的长期平台层”

原因很具体：

- `memory-search-tool.ts` 超过三千行；
- 里面同时承担路由、精确键识别、远端查询、回退、融合、诊断、上下文拼装；
- 这种写法适合快速推进实验，不适合长期演进。

它现在已经能证明方案有效，但如果直接把这个形态原样带进 `W5`，后面迭代成本会越来越高。

### 4. 本地层在这套方案里应该被重新定位

当前设计文档经常把本地层称为“默认与兜底”，但从实现和结果看，它其实承担了三件更重要的事：

1. 质量锚点：没有它，很多精确键与基础记忆体验会变脆。
2. 回滚锚点：slot 独占条件下，bridge 必须把它内置。
3. 可解释锚点：文件路径、行号、二次读取语义都来自这里。

所以它不该只是“fallback”，更应该被正式定义成“基础记忆层”。

### 5. `Gate-4` 的评测方法总体是好的，但数据集已经开始接近饱和

`variant` 在最终结果里已经接近全桶 `1.0`。这说明：

- 当前评测足以筛掉明显坏设计；
- 但再往后，它对“更细的质量差异”会越来越迟钝。

这不是当前方案失败，而是评测体系进入下一阶段后需要升级。

## 回答 10 个关键问题

### 1. 当前 `builtin + Mem0 + Graphiti` 三层体系是否是合理方向？

**是，方向合理。**

原因：

- 它尊重了 `OpenClaw` memory slot 独占现实；
- 它没有把全部希望押在单一远端；
- 它把本地、作用域事实、时序关系分成了三层。

### 2. local fallback 现在的定位是否正确？

**基本正确，但命名偏保守。**

更准确的叫法应是：

> `local` 不是单纯 fallback，而是基础记忆层；fallback 只是它的一个角色。

### 3. `Mem0` 在方案中的真实价值是什么？

**真实价值是作用域化事实记忆与写入治理。**

它最适合：

- 用户偏好
- 长期事实
- 具备 `user_id / agent_id / run_id` 范围的问题

它不该被强行当成时序图搜索引擎。

### 4. `Graphiti` 在方案中的真实价值是什么？

**真实价值是时序关系、图侧关联、焦点节点重排。**

它最适合：

- timeline 问题
- 关系问题
- 需要“围绕某个实体重新聚焦”的问题

### 5. 当前三路融合与重排设计是否优秀，还是只是勉强可用？

**当前结论：好用，但还不能叫优秀。**

优点：

- 已经证明能把质量拉上去；
- 已经能通过时延与稳定性门禁；
- 已经具备一定可解释性。

缺点：

- 融合权重靠手工静态规则；
- bucket 识别靠规则分类；
- 还没有充分利用官方命名空间能力。

### 6. 当前方案中最大的设计缺陷是什么？

**最大的设计缺陷是：桥接层承担了过多策略职责。**

这导致：

- 路由、融合、回退、诊断、上下文拼装耦合；
- 一个策略变化会波及很多逻辑；
- 长期维护成本高。

### 7. 当前方案中最大的实现缺陷是什么？

**最大的实现缺陷是：很多关键策略还是“手工规则 + 经验值”，没有抽成能力层。**

例如：

- query typing 靠正则；
- fusion policy 靠静态权重；
- Graphiti 查询范围还没用 `group_ids`；
- Aura 连接规整是隐式行为，不是显式部署策略。

### 8. 当前方案中最值得继续保留的 3 个点是什么？

1. `local-first + bridge 内置 fallback`
2. `Mem0` 的作用域主键设计
3. `Gate-4` 的冻结门禁方法

### 9. 当前方案中进入 `W5` 前最该修的 3 个点是什么？

1. 把 bridge 按职责拆层
2. 把 `Graphiti` 查询范围治理做成正式能力
3. 把部署型补丁变成显式运行策略

### 10. 最终结论是什么？

**可以进入 `W5`，但需带着风险清单。**

## 这套方案做得好的地方

### 优点 1：尊重 `OpenClaw` 现有架构边界

它没有试图和 `memory slot` 独占机制对抗，而是顺着这个约束，把 bridge 做成一个真正接管 memory slot 的层，并把本地 fallback 内建进去。

这是正确的工程做法。

### 优点 2：本地层不是被废掉，而是被保留下来

这是这套方案最大的韧性来源。

如果当时直接把系统设计成“全部走远端”，那 `W4` 大概率根本收不了口。

### 优点 3：`Mem0` 与 `Graphiti` 的分工是有辨识度的

不是“两个远端一起搜谁强算谁”，而是：

- `Mem0` 更偏事实与范围；
- `Graphiti` 更偏关系与时序；
- bucket 与 routing 不是完全乱来的。

### 优点 4：诊断能力比很多试验型方案强

当前 bridge 已经能给出：

- 路由轨迹
- 回退原因
- `http_4xx` / `http_5xx` / `timeout` 这类失败分类

这说明它已经从“黑盒试验”走向“可调试系统”。

### 优点 5：评测纪律扎实

最值得肯定的是：

- 硬门禁不放水；
- `NO-GO` 不是失败，而是设计反馈；
- 最后 `GO` 不是靠改口径拿到的。

## 这套方案的缺陷与风险

### 设计缺陷 1：桥接层过于臃肿

`memory-search-tool.ts` 已经超过三千行。

这不是“文件有点长”的问题，而是职责边界已经混在一起：

- 查询识别
- 路由
- 远端调用
- 回退
- 融合候选构造
- 融合排序
- 上下文拼装
- 诊断输出

这会直接影响 `W5` 的演进速度。

### 设计缺陷 2：策略过于依赖静态规则

现在很多关键策略都是“先写死一版”：

- query 类型靠正则
- bucket 靠规则
- source 权重靠静态表

这在 `W4` 是合理的，因为先要收敛；
但进入 `W5` 后，如果不继续抽象，会越来越难调。

### 设计缺陷 3：没有充分利用 `Graphiti` 官方命名空间能力

官方已经明确说 `group_ids` 可以缩小搜索空间并提升性能。

当前没用这条能力，意味着：

- `W4` 的 `p95` 是靠减少查询量、减少取回数压下来的；
- 但还没真正动到 `Graphiti` 搜索空间治理这层。

### 实现缺陷 1：部署策略与产品策略混在一起

例如：

- `DashScope text-embedding-v4@1536`
- 禁止 `18082`
- `Aura` 自动改 `bolt+s`

这些对当前部署是有效的，甚至是正确的；
但它们还没有被整理成“显式运行画像”，而是部分直接写进脚本与默认行为。

### 实现缺陷 2：`Aura` 连接策略与官方默认建议有偏离

`Neo4j` 官方把 `neo4j+s` 视为 `Aura` 的常见默认方案；
当前本地脚本会自动改成 `bolt+s`，这说明：

- 这是一种本地兜底工程修复；
- 但不应该长期以“隐式重写用户配置”的方式存在。

### 实现缺陷 3：评测集开始饱和

`variant` 现在已经接近满分，说明这套评测集以后更适合作为回归门，已经不太适合继续做细粒度质量比较。

## 分项评价

### 架构评价

**评价：方向正确，层次清晰，但桥接过重。**

### 质量评价

**评价：强。**

当前方案已经证明，它可以稳定提升记忆检索质量，而不是仅仅追求低时延。

### 速度评价

**评价：已达标，但尾延迟仍是长期主题。**

`day33` 已经过线，但它说明的是“当前压住了”，不代表“这类问题已经从架构上消失”。

### 稳定性评价

**评价：中上。**

已经达门禁，但仍依赖外部服务、远端图查询和部署细节。

### 可观测性评价

**评价：中上。**

桥接诊断已经比很多同类方案强，但还缺更统一的生产化视角。

### 可维护性评价

**评价：中等偏弱。**

这是当前最明显的短板。

## 面向 `W5` 的建议

### 可以放心带进 `W5` 的东西

1. `local-first` 的分层方向
2. `Mem0` 的作用域化搜索设计
3. `Graphiti` 的时间关系定位
4. `memory_search` 硬门禁
5. `Gate-4` 单变量收口方法

### 进入 `W5` 时必须显式带着的风险

1. `Graphiti` 长尾仍是第一性能风险
2. bridge 代码结构会拖慢后续演进
3. `group_ids` 是高价值优化点，但当前社区存在多组检索缺陷风险
4. `Aura` 连接策略要显式文档化，而不是继续靠隐式重写
5. 当前评测集需要升级，避免长期“满分但盲区变大”

### 我建议的 `W5` 开场顺序

1. **先冻结 `day33` 为 `W5` 基线**
2. **再拆 bridge 职责**
3. **然后做 `Graphiti` 查询范围治理**
4. **最后再扩更复杂的融合策略**

顺序不能反。否则又会回到“先加能力，再补稳定性”的旧路。

## 审计结论

这套 `OpenClaw Mem0 + Graphiti` 升级方案，经过 `W4` 最终收口后，可以做出一个比较清楚的判断：

> **它不是一套失败后勉强修补的方案，而是一套已经证明方向正确、但仍需工程润色才能长期放大的方案。**

如果问题是：

- “值不值得继续做？”——**值得。**
- “能不能直接一路放大？”——**还不能。**
- “是否可以进入 `W5`？”——**可以，但必须带着风险清单进入。**
